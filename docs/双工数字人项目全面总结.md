# audio_dual_avatar 双工数字人项目全面总结

> 审计日期：2026-11-19
> 审计范围：`audio_dual_avatar/deployment`、`audio_dual_avatar/docs`，并交叉核对核心源码、README、安装记录和当前运行状态。
> 约束：本文只做项目归纳、审计和测试，没有修改业务代码。

## 1. 项目定位与结论

`audio_dual_avatar` 是一个由 MiniCPM-o 4.5 和 MuseTalk v15 组成的全双工数字人系统。MiniCPM-o 负责接收用户语音、理解对话、生成文本和流式语音；MuseTalk 接收这些语音片段，实时生成口型同步的视频帧。Gateway 把模型会话、数字人视频、音频片段、前端页面和平台接入接口统一起来。

项目已经具备从安装、权重校验、形象预处理、服务启动、实时交互、形象切换、视频编码、停止清理到实验诊断的一整套实现。当前服务可以完成真实的 H.264 全链路会话，四个基础服务和 GPEN 修复进程均可健康运行。

本次复测的直接证据如下：

- MuseTalk 测试：正确设置包路径后 `65 passed`，有 1 个 Starlette/httpx 弃用警告。
- H.264 全链路 smoke：会话成功协商 `768×1344 @ 24 FPS`，收到 1,482 个 `MTH1` 视频包、18 个 `MTA1` 音频包，生成视频帧 427 个，无会话错误。
- 无头浏览器检查：`/avatar` 返回 HTTP 200，页面显示服务就绪，未发现页面异常或失败请求。
- 当前健康状态：MuseTalk 为 `ready`，Gateway、Backend、Worker 为 `healthy`，GPEN 子进程存活。

## 2. 总体架构

```text
浏览器 / 平台
   │
   ├─ 页面：/avatar、/avatar-v2、/omni
   ├─ 公共会话：POST /v1/avatar/sessions
   │              WSS /v1/avatar/sessions/{id}/stream
   └─ 兼容接口：WSS /v1/realtime、/avatar-live/ws/live
          │
          ▼
Gateway :8006
   ├─ Worker 排队与会话编排 :22400
   ├─ MiniCPM-o Backend :22500  —— GPU0
   └─ AvatarBridge
          │ 旁路 MiniCPM 流式音频
          ▼
MuseTalk stream server :8000 —— GPU2
   ├─ Whisper 特征与音频窗口
   ├─ MuseTalk UNet + SD-VAE
   ├─ 可选 GPEN-BFR-512 修复
   └─ WebP 或 H.264 视频输出
```

核心调度关系是：MiniCPM-o 产生一段流式语音，Gateway 将语音原样旁路给 MuseTalk；MuseTalk 按语音窗口生成口型帧；同一个响应由 `response_id` 和媒体 segment 关联。用户打断时，MiniCPM 进入强制监听，数字人侧清理旧 segment，并通过 flush/版本号避免旧帧继续进入编码器。

运行时分为两个 Python 环境：

| 环境 | 用途 | 典型组件 |
|---|---|---|
| `audio_dual_avatar/.venv` | 实时服务 | Python 3.10、torch 2.8.0+cu128、transformers 4.51.0、diffusers 0.30.2、MiniCPM、MuseTalk runtime、Gateway |
| `musetalk_project/venv` | 新形象预处理 | torch 2.1、torchvision 0.16、mmcv 2.1、mmpose 1.3.2、DWPose/S3FD |
| 外部 GPEN 对齐环境 | 离线准备 GPEN 对齐缓存 | `facexlib` 等检测/对齐依赖；在线 GPEN 不依赖该临时环境 |

## 3. 已实现的主要功能

### 3.1 MiniCPM-o 全双工交互

MiniCPM 侧提供聊天、流式和双工推理接口。数字人默认使用 `mode=audio`，输入为单声道 16 kHz PCM，输出包含监听状态、文本增量和 24 kHz 语音。Gateway 支持排队、Worker 分配、会话状态、输入 ACK、强制监听和断开清理。

`/avatar` 是面向数字人的纯音频页面；`/omni` 保留摄像头输入、Metrics、录制和更完整的 Omni 能力。MiniCPM 自己的播放器保持静音，数字人播放器负责最终的模型语音播放和音画同步。

### 3.2 公共 Avatar Session API

推荐接入方式是单连接 API：

```http
POST /v1/avatar/sessions
WSS  /v1/avatar/sessions/{session_id}/stream?token=...
```

创建请求可指定 `preset_id`、系统提示词、视频编码偏好和业务 metadata。Gateway 内部完成形象激活、提示词和音色解析、Worker 分配、MiniCPM 会话以及 MuseTalk viewer 编排。WebSocket 同时承载：

- JSON 控制和状态事件；
- `MTA1` WAV 音频片段；
- `MTH1` H.264 或 `MTF1` WebP/JPEG 视频帧。

Browser SDK 负责麦克风采集、Base64 编码、WebCodecs 解码、AudioContext 排程、音画同步、ACK、打断和清理。单机当前限制为一个活动数字人会话。

### 3.3 数字人形象管理

项目通过 avatar preset 把四类资源绑定在一起：视频缓存、参考音频、系统提示词和展示信息。现有能力包括：

- 列出有效/无效缓存；
- 会话前切换形象；
- `add_avatar.sh` 从视频生成新形象；
- 用户自定义形象任务和状态查询；
- 管理员删除形象并检查共享资源引用；
- YAML 热加载 preset；
- 在 GPEN 模式下为形象准备离线对齐缓存。

历史安装记录确认当前有三套有效缓存：

| 形象 | 输出尺寸 | 循环帧数 |
|---|---:|---:|
| `knowledge_host_720p` | 768×1344 | 690 |
| `musetalk_test_avatar` | 480×864 | 690 |
| `ecommerce` | 768×1344 | 690 |

### 3.4 MuseTalk 流式视频管线

MuseTalk 使用缓存的源帧、bbox、mask、latent 等数据，结合 Whisper 音频特征，通过 UNet 和 SD-VAE 生成 256×256 的口型区域，再缩放并贴回原视频画面。当前配置为 24 FPS，并采用 legacy Whisper 窗口和 jaw parsing mask。

实时 viewer 管理自己的音频、生成、修复、合成、编码和网络队列。H.264 路径使用有序提交，保持 segment ID、帧序和 PTS；flush、形象版本和取消状态会在多个队列边界检查，防止打断后的旧帧泄漏。WebP/JPEG 路径仍保留用于兼容和调试。

### 3.5 H.264 与 WebP 媒体协议

H.264 是默认的视频输出路径，使用 ffmpeg/libx264 编码 Annex-B access unit，浏览器通过 WebCodecs 解码。H.264 帧使用 `MTH1`，图片帧使用 `MTF1`；音频片段使用 `MTA1` 加完整 WAV 文件。服务端支持 IDR、flush 和查询参数选择 `video_codec=h264|webp`。

历史和本次测试均验证了 H.264 数据可被 ffmpeg 完整解码；浏览器检查验证了页面和资源加载，但真实浏览器 WebCodecs 播放、音画体验和回声消除仍需要在目标客户端环境继续验证。

### 3.6 GPEN 实时人脸修复

GPEN-BFR-512 是可选的人脸修复层，处理路径为：

```text
MuseTalk 生成 256 crop
  → 对齐到 512
  → GPEN
  → 逆变换
  → bbox 缩放与原 mask 贴回
  → H.264 编码/网络发送
```

实现特点：

- GPEN 常驻加载、权重和算子校验、启动预热；关闭时回到原始 MuseTalk。
- 只处理生成帧，待机帧、静音旁路和 hold 帧沿用原逻辑。
- 支持与 MuseTalk 共进程线程模式，也支持独立 GPEN 子进程。
- `GPEN_CUDA_VISIBLE_DEVICES` 支持物理 GPU 映射；启动器会合并可见设备并映射逻辑 CUDA 设备。
- 通过小容量队列、flush 序号、形象版本和取消集合丢弃过期结果。
- 在线不依赖人脸检测或临时文件；每个形象需要预先生成 `gpen_alignment.npz`。
- `/api/status` 暴露 GPEN 设备、执行模式、调用帧数、模型均值、RPC 均值、IPC 均值和最近耗时。

离线对比显示 GPEN、GFPGAN、CodeFormer 各有取舍：GPEN 的单帧模型耗时较低，但修复结果、肤色和身份保持不能只用单一指标判断；CodeFormer 的保守权重和嘴周区域保留在部分实验中更稳定；颜色校正不适合默认开启。

## 4. 部署与运维实现

### 4.1 安装和启动

根目录脚本负责安装虚拟环境、固定依赖、ffmpeg、TLS 证书、模型权重和 SHA256 校验。启动脚本负责：

1. 读取 `.avatar-env`；
2. 计算 MiniCPM、MuseTalk、GPEN 的 GPU 可见性和逻辑设备；
3. 启动 MuseTalk；
4. 启动 MiniCPM 的 Backend、Worker 和 Gateway；
5. 轮询健康接口；
6. 提供 `status`、`stop` 和重启流程。

关键服务端口：

| 端口 | 服务 | 用途 |
|---:|---|---|
| 8006 | Gateway HTTPS | 页面、公开 REST、WebSocket |
| 8007 | Gateway 内部 HTTP | 内部服务注册/管理 |
| 22400 | Worker | 推理任务和 Worker 健康检查 |
| 22500 | MiniCPM Backend | 模型推理 |
| 8000 | MuseTalk | 内部音频桥、viewer 和状态接口 |

### 4.2 停止和生命周期

历史排查发现，Uvicorn 默认不限制 graceful shutdown 时长时，公开端口可能一直等待未完成连接，外层脚本最终通过 SIGKILL 结束进程。当前公开和内部 Uvicorn 均设置 10 秒优雅关闭上限，外层仍保留 30 秒保护。历史回归结果为关闭测试 2 项通过，完整 stop 返回 0，耗时约 1.88 秒；本次不重复执行会停止当前服务的测试。

本次直接执行 `tests/test_service_lifecycle.sh` 时出现一次端口 10007 未在等待窗口内释放的失败。该结果应作为当前环境的验证限制记录；它与历史完整 stop 成功记录并存，不能据此断言所有生命周期路径均已失败。

### 4.3 权重、缓存和依赖

历史安装审计确认清单中的 36 个权重文件 SHA256 全部通过。预处理环境 `pip check` 通过；实时环境按照上游锁文件使用 `--no-deps`，仍保留上游已知的 `minicpmo-utils`/librosa 版本声明冲突，因此不能把实时环境的 pip 检查描述为完全无冲突。

默认 720p 和电商缓存曾与某个 Git 提交不一致，安装记录已通过独立预处理环境从项目内视频重新生成。部署时应以实际缓存状态和 `avatars` 接口为准，不应只依赖 README 中的静态描述。

## 5. 实验与测试归纳

### 5.1 基础安装和全链路验证

历史安装记录覆盖：模型校验、预处理导入、DWPose/S3FD 加载、MMCV CUDA NMS、浏览器依赖、三套形象缓存、WebP/H.264 会话、H.264 解码和服务健康检查。

典型历史结果：

- WebP 会话：1,398 个视频包、22 个语音包、521 个 MuseTalk 生成帧。
- H.264 会话：1,811 个视频包、5 个语音包、105 个生成帧；ffmpeg 完整解码 1,811 帧。
- 单 GPU 0 验证：1,777 个视频包、5 个语音包、100 个生成帧；浏览器检查通过；停止无 SIGKILL。

本次复测使用当前运行服务完成：

- `PYTHONPATH=musetalk_project/MuseTalk .venv/bin/pytest -q musetalk_project/MuseTalk/tests`：65 passed。
- `AVATAR_SMOKE_CODEC=h264 .venv/bin/python deployment/smoke_session.py`：H.264 会话、18 个媒体 segment、427 个生成帧、1,482 个视频包、18 个音频包，无错误。
- `deployment/browser-venv/bin/python deployment/check_browser.py`：页面 200，无页面错误、无失败请求。

### 5.2 关停回归

`deployment/diagnose_gateway_shutdown.py` 与历史记录共同验证了挂起 HTTP 请求时的关停问题及 10 秒 timeout 修复。该实验的价值在于确认应用清理会执行、公开/内部端口会释放，并且不会等到外层 30 秒保护强杀。

### 5.3 MuseTalk 256/320 尺寸与 VAE 诊断

320 实验复用了已有 256 形象的源帧、坐标和 mask，只重新生成 320×320 latent，得到 40×40 latent 张量；完整 H.264 smoke 成功，生成 raw 图为 320×320。实验说明尺寸调整可以单独隔离 latent 影响，但并没有证明 320 配置在实时吞吐、身份保持或最终画质上优于 256。

256 VAE 诊断比较了 posterior-mode 重建、缓存 reference latent 解码、直接 UNet+VAE 输出、bbox 尺寸变体和对照图。结果显示 VAE 会带来轻微柔化，UNet 输出会进一步影响下脸区域；这些结果用于定位画质来源，不等价于产品画质结论。

### 5.4 GPEN/GFPGAN/CodeFormer 离线对比

恢复实验覆盖 GFPGAN、GPEN-BFR-512 和 CodeFormer 不同权重，以及：

- 全脸修复与原图区域保留；
- 生成 landmark 与源 landmark；
- 嘴周区域限制；
- feather 边界融合；
- Lab 颜色校正；
- 固定音频、idle 边界、24 FPS 视频和音频解码。

主要结论：

- GPEN 在线模型阶段在隔离条件下约 15–21 ms，但共享 GPU、CPU 合成、锁和进程边界会显著改变端到端耗时。
- CodeFormer 保守权重在部分头像和区域指标上更稳，但仍不能作为所有头像的统一最优方案。
- 嘴周区域保留和 feather 融合能降低部分源脸误差。
- 颜色校正对不同头像不一致，应保持可选。
- 修复延迟、身份保持、局部皮肤误差和时间抖动需要同时评估，不能只看单帧视觉锐度。

### 5.5 GPEN 流式、独立进程与异步管线

实验按阶段演进：

1. **同进程流式 GPEN**：验证模型接入、CUDA/native 算子一致性、缓存校验、形象切换和真实全双工会话。
2. **GPU 物理映射**：支持 MiniCPM、MuseTalk、GPEN 分卡，避免逻辑 CUDA 设备误映射。
3. **GPEN 独立进程**：隔离 GPEN forward、GPU/CPU 边界和父进程的 finalize/composite，模型阶段从约 44–52 ms 降至约 15–16 ms；RPC 约 27 ms，IPC 残差约 11 ms。
4. **异步恢复/合成**：raw→restore→composite→fused 多队列重叠，真实 paced 测试约 19.90 FPS，修复约 49.70 ms、合成约 18.59 ms，未证明稳定 24 FPS。
5. **三阶段管线**：拆分输入对齐、GPEN、逆变换/贴回；验证了边界和数据正确性，但 GPEN 约 52 ms、输出阶段约 45 ms，仍未形成明确性能收益。

当前 2026-11-19 时延审计的结论是：GPU 分流后，MiniCPM 66 秒测试和完整 Gateway+MuseTalk+GPEN 约 72 秒测试都没有观察到持续累计漂移；但仍存在短时迟到、队列边界、1 秒输入单元和浏览器实际预缓冲造成的抖动风险。

### 5.6 GPEN batch 可行性

真实 512×512 输入的隔离 forward 基准：

| batch | 每批耗时 | 每帧耗时 | 相对 batch 1 |
|---:|---:|---:|---:|
| 1 | 15.16 ms | 15.16 ms | — |
| 2 | 27.67 ms | 13.83 ms | 约降低 9% |
| 4 | 45.34 ms | 11.34 ms | 约降低 25% |
| 8 | 87.25 ms | 10.91 ms | 约降低 28% |

batch 2/4/8 与单帧输出最大差异为 1 个 uint8 level，且基准不含 RPC、打包、解码和未满 batch 的等待。当前没有必要直接改成 batch；若要继续降低调用和 IPC 开销，应优先验证 batch 4，并补充 timeout flush、帧序和 1 LSB 差异的产品验收。

## 6. 当前性能和队列边界

当前时延审计中使用的关键口径：

- GPEN 模型阶段：约 15.74 ms 均值。
- GPEN RPC：约 27.01 ms 均值；隔离 RPC p50 18.82 ms、p95 19.80 ms、p99 22.04 ms。
- 72 秒完整链路：末端残差约 +0.177 秒，残差斜率约 −0.24 ms/媒体秒。
- 400 帧 paced ACK：两轮最大 PTS 迟到约 444–474 ms；测试不包含真实浏览器解码和音频设备播放。
- H.264 长测试编码约 25.7 FPS，但该数值不能替代真实客户端持续播放帧率。

关键队列的设计意图是有限反压和旧帧淘汰：raw queue 约 2.33 秒，prepared/restored queue 各 2 帧，fused queue 8 帧，H.264 ordered queue 16 帧，network queue 48 帧，服务端 ACK 窗口 96 帧。Gateway 音频桥容量约 256 条消息，满后丢弃；MuseTalk PCM buffer 超过 5 秒会丢旧样本。当前没有持续积压，但队列高水位、等待时长和跨服务缓冲仍不完整可观测。

## 7. 已知限制与后续重点

1. 当前单机只允许一个活动数字人会话；MuseTalk 也按单 viewer/单上游会话设计。
2. 服务端声明 32 帧 prebuffer，但浏览器实际使用首段 8 帧、续段 2 帧；网络抖动时可能出现短暂空档。
3. H.264、WebCodecs、音频播放和回声消除仍需在目标生产浏览器/网络环境进行真实体验验证。
4. GPEN 异步和三阶段实现验证了正确性与边界，尚未证明共享资源条件下长期稳定 24 FPS。
5. GPEN 新形象的对齐缓存目前需要单独准备，尚未完全纳入形象定制任务的自动流程。
6. Gateway 音频桥和 MuseTalk PCM buffer 在高水位时会丢数据；业务层尚缺少统一的高水位、等待时长和丢弃量指标。
7. 实时环境仍有上游已知的依赖声明冲突，应继续以锁文件、实际导入和真实推理验证为准。
8. `tests/test_service_lifecycle.sh` 本次执行出现端口释放等待失败；需要在稳定、隔离的测试环境中单独复现并确认是否为 TIME_WAIT/测试时序问题。

建议的后续优先级是：先补齐浏览器真实播放和端到端逐帧时延观测，再完善队列高水位/丢弃指标，最后评估 GPEN batch 4 或更细的流水线优化。不要用无限扩大队列的方式掩盖实时延迟。

## 8. 推荐使用方式

### 平台接入

优先使用公共 Avatar Session API 或直接嵌入 `/avatar`。需要自定义 UI 时，复用项目 Browser SDK 和播放器；只有确实需要完全控制协议时，才直接实现 `/v1/realtime` 与 `/avatar-live/ws/live` 的内部协作流程。

### 本地运行

```bash
cd audio_dual_avatar
./install.sh
./start_avatar.sh
./start_avatar.sh status
./start_avatar.sh stop
```

默认入口为 `https://127.0.0.1:8006/avatar`。H.264 不兼容时可以请求 `video_codec=webp`。

### 常用复测

```bash
# MuseTalk 单元测试
```

## 10. 审计边界说明

本文把代码静态审计、项目已有实验记录和本次复测结果放在同一份文档中，但三者的证据强度不同：历史报告用于说明实验过程和趋势，本次复测用于确认当前服务仍可运行；离线图像指标不能直接替代真实浏览器体验，隔离 GPU 基准不能直接替代共享 GPU 的端到端时延。涉及性能承诺时，应以对应实验的输入、设备布局、队列口径和客户端行为一起解读。
